# LLM 모델 담당 작업 체크리스트

## 1. 완성 단계부터 정의

**담당 팀원: pi · 담당 영역: LLM 모델**

> **참고 문서 안내(2026-10-20):** 본문은 팀원 분담 확인 전에 pi 기준으로 작성한 체크리스트다. 현재 팀원 원문의 텍스트 담당은 김다혜이며, 실제 담당·일정의 비교 기준과 합의할 내용은 [modelIntegrationReview.md](modelIntegrationReview.md)를 따른다. 이 문서의 pi 표기는 현재 팀 배정이나 일정 합의를 대신하지 않는다.

작성일: 2026-10-20 · 대상: 화장품 광고 생성 MVP · 관련 코드 브랜치: `plan/models`

여기서 LLM 모델 담당은 텍스트 생성뿐 아니라 제품 이미지 관찰에 사용하는 VLM, 프롬프트, 구조화 출력, 문구 검수·재작성, 품질 평가를 포함한다.

pi의 이미지 모델 작업은 [imageTodo.md](imageTodo.md)에서 별도로 관리한다. 누끼·배경 생성·제품 재합성·GPU 실행 검증은 그 문서의 완료 기준을 따른다.

| 단계 | 완성 상태 | 통과 조건 | 남겨야 할 증거 |
| --- | --- | --- | --- |
| 1. 계약 확정 | 팀원이 무엇을 넣고 무엇을 받는지 안다 | 입력·출력·오류·검수 상태·역할 경계를 합의하고, 모델과 평가 기준을 고정했다 | 계약 예제, 모델·프롬프트 설정, 평가셋과 수용 기준 |
| 2. 실제 모델 호출 | 실제 계정에서 각 기능이 동작한다 | 제품 관찰, 광고 후보 생성, 검수, 재작성, 재검수를 실제 지정 모델로 실행했다 | 비밀값을 제거한 요청·응답, request ID, 모델·프롬프트 버전, 실행 결과 |
| 3. 품질 검증 | 정상·실패 사례에서 합의한 품질을 충족한다 | 고정 평가셋으로 사실 근거, 검수 누락·오탐, 구조화 성공률, 지연·비용을 측정하고 기준을 통과했다 | 항목별 평가 결과, 실패 사례, 개선 전후 비교, 비용·지연 측정 |
| 4. 팀 연동 완료 | 다른 담당자가 LLM 기능을 연결해 재현할 수 있다 | 실제 API·DB 흐름에서 revision 변경, 오래된 검수 차단, 오류 전달, 수정 후 재검수를 확인하고 인계를 완료했다 | 통합 실행 결과, 재현 명령, 인계 문서, 팀 확인 기록 |

**pi의 LLM 담당 완료는 4단계까지 충족한 상태로 정의한다.** 4단계는 API·DB 담당과 함께 확인한다. SDK import, 래퍼 구현, 모의 응답 단위 테스트만으로 완료 처리하지 않는다. 이미지 모델 완료는 `imageTodo.md`, 서비스 전체 배포와 UI 완성은 해당 담당의 완료 기준을 따른다.

### 최종 완료 체크

- [ ] 1~4단계의 산출물과 확인 날짜가 기록돼 있다.
- [ ] 필수 기능과 실패 사례가 고정 평가셋의 수용 기준을 통과했다.
- [ ] 미해결 필수 오류가 없고, 남은 제한사항은 담당자·영향·후속 작업을 명시했다.
- [ ] 팀원이 문서의 명령과 입력 예제로 실제 호출·검수·재검수를 재현했다.
- [ ] API·DB 담당이 저장된 검수와 최신 입력의 일치 여부를 확인했고, PM이 담당 범위 완료를 확인했다.

## 3. pi의 책임과 협업 경계

| 업무 | pi 책임 | 함께 맞출 담당 |
| --- | --- | --- |
| 모델 선정·호출 | 텍스트/VLM/검수 모델 설정, 출력 형식, 오류·시간 제한, 비교 평가 | API 담당: 설정 주입과 클라이언트 생명주기 |
| 제품 관찰 | 이미지에서 관찰 가능한 특징과 불확실성 반환 | 자산/API/UI 담당: 이미지 검사, 소유권, 사용자 확인·저장 |
| 광고 문구 | 확인된 사실에 근거한 후보 생성, 채널·톤 반영, 재작성 | 기획/UI 담당: 사용자 선택값과 편집 흐름 |
| 검수 | 규칙 적용, LLM 검수, 근거·불확실성·상태 반환 | 정책 검토 담당: 규칙 내용 검토 / API·DB 담당: 최신성·승인 이력 |
| 평가·인계 | 평가셋, 회귀 평가, 실패 분석, 호출 예제, 품질·비용 보고 | PM: 수용 기준 / 백엔드 담당: 통합 실행 |
| 이미지 작업 연결 | 문구·비주얼 요구사항의 전달 계약 협의 | `imageTodo.md`의 이미지 모델 작업 및 API·인프라 담당과 연결 |

이미지 생성·누끼 구현과 GPU 실행 검증은 `imageTodo.md`에서 관리한다. 레이아웃·렌더링, 인증·DB·SSE, 인프라 운영은 해당 담당과 연결 계약 및 검증 결과를 함께 확인한다. 별도 요구가 없는 파인튜닝·자체 모델 학습·RAG 구축은 이번 필수 범위에 포함하지 않는다.

## 4. 단계별 실행 체크리스트

### 단계 1-A. 요구사항과 계약 확정

**산출물:** LLM 계약 예제, 담당 경계, 평가 기준. **의존:** PM·API·기획 담당과 입력값 및 완료 기준 합의.

- [ ] MVP에서 지원할 언어·시장·채널·톤·문구 길이와 금지 조건을 정한다.
- [ ] 사용자가 선택한 타깃을 `AdOptions.target`으로 받으며, 모델이 고객군·구매 행동을 사실처럼 추정하지 않도록 한다.
- [ ] `ProductObservation`은 관찰 제안, `ProductFacts.confirmed_claims`는 외부에서 확인한 사실이라는 경계를 합의한다.
- [ ] 모델이 확인된 사실의 `claim_id`·`evidence_ref`·기능성 분류를 새로 만들거나 승인하지 않도록 한다.
- [ ] 입력이 비었거나 필수 근거가 부족할 때의 동작을 정한다. 누락 정보를 모델 추측으로 채우지 않는다.
- [ ] 정상 요청·응답과 `no_flags`, `warnings`, `blocked`, `unavailable` 예제를 API 담당에게 제공한다.
- [ ] `warnings`의 사람 검토 절차, 승인 주체·이력, 재검수 조건을 합의한다. 현재 helper를 건너뛰는 임시 우회로 처리하지 않는다.
- [ ] 자동 재작성은 초기 MVP 기준 최대 1회로 제안하고, 횟수·예산·종료 조건을 팀과 확정한다.
- [ ] 평가 항목별 수용 기준과 측정 조건을 먼저 기록한다. 목표 수치가 미정이면 해당 완료 항목은 체크하지 않는다.

### 단계 1-B. 모델과 실행 설정 확정

**산출물:** 모델 비교표, 서버 설정 예제, 프롬프트 버전 규칙. **통과:** 실제 계정의 지원 기능을 확인하고 재현 가능한 설정을 남김.

- [ ] 후보 모델을 동일 입력으로 비교한다: 한국어 문구, 이미지 관찰, 구조화 출력, 검수, 응답 시간, 비용.
- [ ] 실제 계정에서 모델 ID와 Responses API·Structured Outputs·이미지 입력 지원 여부를 확인한다.
- [ ] 텍스트·VLM·검수 모델을 각각 명시한다. 동일 모델을 재사용하면 그 결정도 기록한다.
- [ ] 프롬프트를 기능별로 관리하고, 변경 시 버전이 바뀌도록 한다.
- [ ] 모델·프롬프트 변경이 검수 스냅샷과 평가 기록에 반영되는지 확인한다.
- [ ] API 키는 서버 환경변수에서 읽고, `.env.example`에는 실제 키를 넣지 않는다.
- [ ] 동시 호출 수, 전체 시간 제한, SDK 재시도, 요청별 토큰·비용 상한을 정한다.
- [ ] SDK 클라이언트 생성·종료 주체를 API 담당과 맞추고, 실행 예제에서 연결을 정상 종료한다.

### 단계 2-A. 제품 이미지 관찰

**대상:** `analyze_product` · **산출물:** 실제 이미지 입력별 `ProductObservation`과 실패 예제.

- [ ] 지원하는 이미지 수와 형식을 계약에 맞추고, 용기 형태·보이는 색·읽히는 라벨을 반환한다.
- [ ] 흐림·반사·가림·작은 글씨·라벨 없음 사례에서 `null` 또는 `uncertainties`를 남긴다.
- [ ] 보이지 않는 성분·효능·인증·기능성을 추정해 확정하지 않는지 확인한다.
- [ ] 이미지/라벨 안의 명령 문장을 지시로 수행하지 않도록 프롬프트와 평가 사례를 준비한다.
- [ ] 자산 담당과 이미지 용량·디코딩·재인코딩·접근 권한 검사 경계를 정한다.
- [ ] 관찰 결과를 사람이 확인한 후 제품 사실로 저장하는 흐름을 API·UI 담당과 연결한다.

### 단계 2-B. 광고 후보 생성

**대상:** `draft_campaign` · **산출물:** 대표 제품·채널별 후보 1~3개와 근거 연결 결과.

- [ ] 요청한 수만큼 후보를 만들고, 각 후보의 콘셉트·핵심 메시지·문구를 구분한다.
- [ ] `headline`, `subheadline`, `cta`, `caption`, `hashtags`, `badges`를 계약에 맞게 반환한다.
- [ ] 타깃·톤·채널·시장 조건과 확정한 길이 제한을 적용한다.
- [ ] 없는 효능·성분·수치·할인·인증·추천 사실을 만들어 내지 않는지 평가한다.
- [ ] `used_claim_ids`가 실제 Claim ID를 가리키는지 검사한다.
- [ ] Claim ID가 존재해도 문장이 그 근거를 넘어설 수 있으므로, 문구와 근거의 의미 일치도 평가한다.
- [ ] 파싱 실패·필수 필드 누락·후보 수 오류를 정상 광고로 반환하지 않는다.

### 단계 2-C. 규칙집과 문구 검수

**대상:** `RulePack`, `review_copy`, `ReviewService.review` · **산출물:** 검토된 규칙집, 검수 상태별 실제 결과.

- [ ] 규칙별 ID, 출처·버전·조항, 적용 대상, 예외, 심각도를 정리한다.
- [ ] 정책 검토 담당의 확인 후에만 규칙집을 `reviewed`로 지정하고 버전·검토 시점을 기록한다.
- [ ] 사용자나 LLM이 정규식·규칙 검토 상태를 임의로 지정하지 못하게 한다.
- [ ] 여섯 문구 필드를 모두 검사한다. 해시태그·배지와 복수 목록 항목도 포함한다.
- [ ] LLM이 정규식에서 발견한 경고·차단 이슈를 삭제하지 못하는지 확인한다.
- [ ] 이슈의 `field`, `quote`, `rule_ids`가 실제 문구·규칙과 일치하는지 검사한다.
- [ ] 정상·경고·차단·검수 불가를 각각 재현하고 `uncertainties`를 보존한다.
- [ ] 규칙집 미검토·누락, 모델 거절·실패를 이슈 없음으로 바꾸지 않는다.
- [ ] `no_flags`는 자동 검사에서 이슈가 없다는 뜻으로 전달한다. `legal_approval=False`를 유지한다.

### 단계 2-D. 재작성과 재검수

**대상:** `rewrite_copy`와 호출 흐름 · **산출물:** 수정 전후 문구, 검수 결과, 종료 이유.

- [ ] 이슈와 제품 사실을 바탕으로 수정하되, 새 효능·근거를 추가하지 않는다.
- [ ] 재작성 결과를 미검수 문구로 취급하고 copy revision을 갱신하도록 API 담당과 맞춘다.
- [ ] 재작성 뒤 정규식·LLM 검수를 모두 다시 실행한다.
- [ ] 합의한 자동 재작성 횟수와 호출 예산을 넘지 않게 한다.
- [ ] 차단·불확실성이 남으면 사람이 수정할 수 있도록 결과를 반환하고 자동 루프를 종료한다.
- [ ] 사용자가 직접 문구를 바꿔도 기존 검수가 무효화되고 재검수가 필요한지 확인한다.

### 단계 3-A. 실패 처리와 호출 기록

**대상:** 게이트웨이 오류, `CallMeta`, API 연결 · **산출물:** 실패별 기대 동작과 관측 기록.

- [ ] 인증 오류, 429, 공급자 장애, 시간 초과, 거절, 불완전 응답, 스키마 오류를 구분한다.
- [ ] 오류의 재시도 가능 여부를 정하고, SDK 재시도 위에 무조건 재시도를 중첩하지 않는다.
- [ ] 동시성 제한과 전체 시간 제한이 실패 상황에서도 지켜지는지 확인한다.
- [ ] `provider_request_id`, 모델, 프롬프트 버전, 처리 시간, 입력·출력 토큰을 기록한다. 없는 값은 미확인으로 남긴다.
- [ ] 호출 비용을 산정한다면 적용 단가·확인일·계산식을 기록하고, 관측 토큰과 추정 비용을 구분한다.
- [ ] API 키, 인증 헤더, 원본 업로드 URL, 개인정보가 기본 로그에 노출되지 않는지 확인한다.
- [ ] 장애를 성공 응답으로 숨기지 않고, API·UI가 표시할 실패·재시도 상태를 전달한다.

### 단계 3-B. 고정 평가셋과 품질 개선

**산출물:** 버전이 있는 평가셋, 수용 기준표, 결과 보고서. **통과:** 합의한 필수 기준을 모두 만족.

- [ ] 정상 제품, 미확인 기능성, 근거 부족, 흐린 이미지, 혼합 언어, 목록 필드, 입력 주입 공격 사례를 포함한다.
- [ ] 각 사례에 입력·기대 상태·판정 근거·사람 검토 기록을 붙인다. 정답을 모르면 미확인으로 남긴다.
- [ ] 프롬프트 수정에 쓰는 개발셋과 최종 평가셋을 구분하고, 평가셋 버전과 변경 이유를 기록한다.
- [ ] 구조화 출력 성공률, 근거 없는 주장 발생, 검수 미탐·오탐, 재작성 후 개선 여부를 측정한다.
- [ ] 한국어 자연스러움·채널 적합성·콘셉트 구분을 동일한 사람 평가 기준으로 채점한다.
- [ ] 입력 크기·동시성·반복 횟수를 고정해 지연과 비용을 측정하고, 표본 수와 측정 조건을 남긴다.
- [ ] LLM의 자기평가만으로 통과시키지 않고, 규칙 검사와 사람 검토를 함께 사용한다.
- [ ] 모델·프롬프트·규칙집을 바꾸면 고정 평가셋으로 회귀를 확인한다.
- [ ] 실패 사례와 개선 전후 결과를 보존하고, 목표 미달 항목을 완료로 표시하지 않는다.

### 단계 4. API·DB 연결과 인계

**산출물:** 통합 실행 증거, 호출 예제, 알려진 제한사항. **의존:** API·DB 담당의 저장·revision 확인 구현.

- [ ] 제품 사실·문구·옵션·규칙집·프롬프트·모델이 달라지면 기존 검수를 무효화한다.
- [ ] 검수 시작 당시 입력과 완료 시점 DB revision을 비교해, 늦게 도착한 결과가 최신 상태를 덮어쓰지 못하게 한다.
- [ ] 내보내기 때 서버가 저장한 검수 결과와 현재 snapshot을 비교한다. 클라이언트가 보낸 report를 승인 근거로 믿지 않는다.
- [ ] `warnings`·`blocked`·`unavailable`의 다음 동작과 사람 검토 필요 여부가 API·UI에 일치하게 전달되는지 확인한다.
- [ ] 제품 확인 → 후보 생성 → 선택/수정 → 검수 → 필요 시 재작성 → 재검수 흐름을 실제 서비스 연결로 실행한다.
- [ ] 문구 수정·재검수만 할 때 불필요한 GPU 이미지 작업이 시작되지 않는지 공동 확인한다.
- [ ] 토큰·request ID·버전·오류가 사용량 집계와 작업 상태에 전달되는지 API 담당과 확인한다.
- [ ] 새 환경에서 설정·설치·실행하는 명령과 정상/실패 입력 예제를 제공한다.
- [ ] 평가 결과, 알려진 한계, 남은 담당자별 작업과 재현 방법을 인계한다.

## 5. 유지해야 할 호출 계약

현재 코드의 계약을 출발점으로 사용한다. 변경이 필요하면 먼저 API·이미지 담당과 합의하고 스키마·예제를 함께 갱신한다. 아래 메서드는 라이브러리 계약이며 HTTP 엔드포인트가 아니다.

| 호출 | 입력 | 출력 | 핵심 조건 |
| --- | --- | --- | --- |
| `analyze_product` | `images: list[str]` | `ModelResult[ProductObservation]` | 관찰과 불확실성을 반환하며 확인된 효능으로 승격하지 않음 |
| `draft_campaign` | `ProductFacts`, `AdOptions`, `count` | `ModelResult[CampaignDraft]` | 후보 1~3개, 문구 필드와 Claim ID 검사 |
| `review_copy` | 사실·문구·옵션·규칙집·정규식 발견 사항 | `ModelResult[LLMReview]` | 이슈 원문·규칙 참조와 불확실성 보존 |
| `ReviewService.review` | 사실·문구·옵션·규칙집·copy revision | `ReviewReport` | 전체 검수 상태와 snapshot·버전 정보를 반환 |
| `rewrite_copy` | 사실·문구·옵션·수정 이슈 | `ModelResult[CopyBundle]` | 반환된 새 문구는 반드시 재검수 |

입력의 `claim_id`, `evidence_ref`, revision과 검수 버전은 서버가 관리할 데이터다. 오류는 `GatewayError.code`, 재시도 가능 여부, 가능한 경우 request ID로 연결한다. 외부 API의 상세 경로·인증·상태 코드는 API 담당과 정하며, `DESIGN.md`의 제안을 이미 구현된 서버로 취급하지 않는다.

## 6. 필수 확인 시나리오

| 수준 | 입력·상황 | 기대 결과 | 실패 기준 |
| --- | --- | --- | --- |
| 단위 | 없는 Claim ID, 잘못된 후보 수 | `GatewayError`의 `INVALID_DOMAIN_OUTPUT` | 잘못된 결과를 정상 출력 |
| 단위 | 원문에 없는 검수 quote를 `ReviewService.review`가 처리 | `unavailable`, `uncertainties`에 `INVALID_REVIEW_REFERENCES` 보존 | 잘못된 검수 근거를 정상 적용 |
| 단위 | 규칙집 미검토, 검수 호출 실패 | 검수 불가 또는 계약상 차단 상태 | `no_flags`로 변환 |
| 실제 모델 | 보이지 않는 라벨·미확인 효능 | 불확실성 표시, 근거 없는 효능 생성 없음 | 추정 사실을 확정해 출력 |
| 실제 모델 | 채널·톤·타깃이 다른 동일 제품 | 확인된 사실을 유지하면서 표현 조건 반영 | 새 사실 생성 또는 조건 무시 |
| 서비스 | 재작성 후 수정된 문구 | revision 갱신 후 전체 재검수 | 이전 검수 재사용 |
| 통합 | 검수 진행 중 사용자가 제품·문구 수정 | 오래된 결과를 현재 검수로 적용하지 않음 | 늦은 응답이 최신 상태를 덮어씀 |
| 통합 | 차단·경고·검수 불가 상태에서 내보내기 시도 | 합의한 차단·사람 검토 절차 적용 | 검수 상태를 무시하고 진행 |
| 통합 | 문구만 수정 | 텍스트 처리만 수행 | 새 GPU 작업이 불필요하게 생성 |

## 7. 먼저 확정할 사항과 실행 순서

- [ ] PM과 필수 채널·시장·언어, 문구 길이, 완료 확인자를 정한다.
- [ ] 정책 규칙집을 검토할 담당자와 최신 출처 확인 절차를 정한다.
- [ ] 실제 계정·예산 안에서 사용할 모델과 평가 호출 한도를 정한다.
- [ ] 품질·지연·비용의 목표 수치, 평가 표본과 통과 조건을 합의한다.
- [ ] 경고 승인 절차, 자동 재작성 횟수, API·DB 담당 및 연동 일정을 정한다.

권장 순서: **계약·평가 기준 확정 → 최소 평가셋 준비 → 실제 모델로 네 기능 연결 → 검수·재작성 흐름 보완 → 고정 평가셋 통과 → API·DB 공동 검증 → 인계**.

체크박스는 산출물과 검증 근거가 있는 경우에만 체크한다. 제안·구현·단위 테스트·실호출·통합 확인을 서로 다른 진행 상태로 기록한다.
