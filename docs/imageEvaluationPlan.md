# 이미지·FinOps 평가 계획 v0.1

2026-10-23 · **임시 기준이며 팀 인수 기준으로 확정되지 않았다. 실제 평가와 추가 유료 호출은 아직 실행하지 않았다.**

[팀 SSOT](https://app.notion.com/p/401b13f77dbd80f39bbccd2e3a489566)의 화장품·인스타그램 4:5·제품 원형 보존·사용자 검토·최종 한 장 흐름과 [PM 서비스 평가 v0.1](https://app.notion.com/p/aaeb13f77dbd83c3a9140157cb49e6df)의 품질·시간·사용성 평가를 실행 가능한 초안으로 구체화했다.
[팀 계획서](https://app.notion.com/p/3fbb13f77dbd807281cefde0aae5c6ea)에 없던 표본 수와 합격 숫자는 이번 제안이다. 원문 자료를 복제하지 않았다.

이 문서의 이미지 품질 100점은 이전 보고서의 **목표 대응도 60점**과 다른 척도다.
코드 테스트 934개, 가상 제품의 실제 이미지 API 호출 7회는 구현·스모크 근거다. 실제품 10종 평가를 수행한 것으로 세지 않는다.

## 1. 종합 비중과 통과 구조

사용자 지시에 따라 **FinOps에 40%**를 둔다.

| 영역 | 종합 비중 | 내부 점수와 필수 조건 |
| --- | ---: | --- |
| 이미지 품질 | 40% | 아래 5차원 100점. 실제품 평가셋·2인 검수·보존 하한·치명 오류·4:5 조건 모두 충족 |
| FinOps | 40% | 성공 광고당 총원가·회피 가능한 낭비·공유 예산·청구 대조의 4개 조건 모두 충족 |
| 서비스 안정성·사용성 | 20% | E2E 성공률·전체 기계 처리 시간·초보 사용자의 완주·텍스트/렌더러 담당 인수 모두 충족 |

종합 점수는 `이미지 × 0.4 + FinOps × 0.4 + 서비스 × 0.2`다.
필수 근거가 미확인이면 점수는 `null`이고 출시 판정은 `BLOCKED`다. 낮은 비용으로 제품 변형을 상쇄하지 않는다.
점수만 넘겼다는 이유로 승인하지 않는다. 각 영역의 필수 조건을 모두 충족한 뒤 담당자와 PM이 인수해야 한다.
모듈이 반환하는 `PROVISIONAL_GATES_MET_AWAITING_TEAM_SIGNOFF`도 서비스 출시나 이미지 자산 승인이 아니다.

## 2. 실제품 평가셋과 표본

| 구분 | 임시 수량 | 사용 방법 |
| --- | ---: | --- |
| 개발 제품 | 실제품 5개 | 프롬프트·오류 처리 개선과 검수자 기준 맞추기 |
| 홀드아웃 제품 | 별도 실제품 5개 | 개선에 사용하지 않은 제품으로 최종 검증 |
| 제품 입력 사진 | 제품마다 2~5장 | 같은 제품의 서로 다른 시점. 권리·출처·파일 해시 기록 |
| 기본/참고 장면 | 제품마다 2조건, 총 20결과 | 기본은 참고 0장, 참고 조건은 배경 1~5장. 10개 참고 조건에 단일·복수 참고를 모두 포함 |
| 반복 비교 | 대표 3조건 × 각 3회 = 9결과 | 기존 결과가 동일 입력·설정이면 3개를 재사용하여 추가 6회. 아니면 별도 9회이며 사전 예산 재계산 |

각 split에 투명·반사·인쇄 라벨과 튜브·펌프·단지 형태를 최소 1개씩 포함한다. 한 제품에 여러 특성이 겹쳐도 된다.
이는 평가 위험과 포장 형태를 넓히려는 조건이다. 서비스가 취급할 수 있는 제품 종류를 제한하거나 무라벨 제품을 금지하는 조건이 아니다.

개발과 홀드아웃은 **제품 단위**로 나눈다. 동일 제품의 다른 사진을 양쪽에 배치하지 않는다. 원본 사진 해시의 재사용도 검사한다.
실제 브랜드 제품의 사진·상표를 쓸 권리와 출처를 확인하고, 비공개 저장소에 둔다. 공개 Git에는 빈 템플릿과 집계 기준만 둔다.
`examples/evaluation/real-product-manifest.template.json`의 10개 슬롯은 모두 `EMPTY_*`, `NOT_COLLECTED`다. 제품·사진·권리를 확보했다는 뜻이 아니다.

홀드아웃 전에 모델, 각 조건의 프롬프트 버전·옵션, 전처리, 평가 기준을 하나의 설정 묶음으로 고정한다.
그 묶음의 SHA-256을 `holdout_settings_sha256`와 각 홀드아웃 결과의 `settings_sha256`에 기록한다.
이 값은 제품과 결과마다 다른 `request_sha256`과 구분한다.
홀드아웃 결과를 보고 프롬프트를 바꾸면 새 평가 주기를 만든다. 기존 점수를 독립 검증 점수처럼 재사용하지 않는다.
최종 20건에 넣는 개발 결과도 같은 동결 설정을 사용해야 한다. 개발 중간 실험은 별도 기록으로 남기고, 변경 뒤 필요한 개발 조건을 다시 평가한다.
이미지·서비스·FinOps의 `evaluation_cycle_id`와 후보 설정 해시가 모두 같아야 종합 점수를 계산한다. 다른 버전의 좋은 결과만 골라 합치지 않는다.

## 3. 이미지 품질 100점

대상은 **한글 광고 문구를 합성하기 전의 이미지 레이어**다. 최종 문구·효능 주장·표현 규정은 김다혜 담당 평가를 취합한다.

| 차원 | 비중 | 1점 | 3점 | 4점 | 5점 |
| --- | ---: | --- | --- | --- | --- |
| 제품 형태 | 25 | 다른 제품·심한 형태 변형 | 알아볼 수 있으나 비례·부품 수정 필요 | 형태·부품 유지, 정체성을 바꾸지 않는 작은 차이 | 원본 비례·실루엣·보이는 부품 충실 |
| 라벨·로고 | 25 | 필수 식별문구/로고 소실·변경 | 읽을 수 있으나 인쇄 오류 수정 필요 | 필수 식별문구·로고 유지, 사소한 비식별 차이 | 글자·위치·로고·원본 인쇄 충실 |
| 색·재질 | 20 | 색이나 재질이 명백히 다름 | 색조·무광/유광 차이 수정 필요 | 원래 색·재질 유지, 작은 조명 차이 | 색·반사·투명도·보이는 질감 충실 |
| 참고·콘셉트 | 15 | 요청 장면과 다름 | 주제는 맞으나 참고 구도·조명 미흡 | 요청 장면과 참고 역할을 대부분 반영 | 다른 제품을 복제하지 않고 구도·조명·콘셉트를 명확히 반영 |
| 구도·카피 여백 | 15 | 잘림·가림·사용 불가 여백 | 배치·여백 수정 필요 | 제품 전체와 요청 배치·여백 확보 | 제품과 후속 카피가 명확하게 분리되고 여백 충분 |

2점은 1점보다는 낫지만 명백한 수정이 필요한 상태다. 각 차원의 더 구체적인 1~5점 기준은 [기계 판독 계획](../examples/evaluation/image-eval-v0.1.json)의 `rating_anchors`에 있다.

점수식은 **`sum(비중 × 사람 점수 / 5)`**다. 모든 차원이 평가됐을 때 최저 20점, 최고 100점이며, 전부 4점이면 정확히 80점이다.
합격 초안은 다음을 모두 충족하는 경우다.

- 총점 **80점 이상**.
- 형태·라벨/로고·색/재질은 각각 **4점 이상**.
- 출력 폭·높이가 기록되어 있고 **정확히 4:5**. 비율 오류는 높은 점수로 상쇄할 수 없다.
- 합의된 치명 오류가 없음. 제품 정체성 변경, 주요 부품 소실, 필수 라벨/로고 변경, 요청하지 않은 제품이나 광고 문구 생성은 점수와 무관하게 실패.
- 서로 다른 사람 2명의 판정이 완료되고, 모든 점수·치명 오류·N/A 판정이 일치하거나 명시적으로 합의됨.

인쇄 없는 제품은 두 검수자가 원본에 인쇄 라벨·로고가 없다고 확인한 경우만 `label_logo=null`, `not_applicable=["label_logo"]`로 기록한다.
나머지 비중 75에 대해 100점으로 재정규화한 **진단 점수**이며 `DIAGNOSTIC_ONLY`로 표시한다. 전체 5차원을 통과했다고 부르지 않는다.
무라벨 제품도 나머지 차원의 80점·보존 하한·치명 오류 조건을 충족해야 한다.
데이터셋 전체에서는 양 split의 실제 인쇄 라벨 제품이 기본/참고 조건을 별도로 통과해야 한다. N/A 결과만으로 라벨 검증을 채우지 않는다.

## 4. 사람 검수 기록

두 사람이 같은 원본·요청·결과를 보고 독립적으로 평가한다. `null`은 모름이며 0점으로 바꾸지 않는다.
서로 점수가 다르면 평균을 내지 않는다. 원본과 결과를 다시 대조하여 최종 점수·치명 오류·N/A와 합의 이유를 기록하고, 두 검수자 ID가 모두 `endorsed_by`에 있어야 한다.
해결되지 않은 의견 차이는 `REVIEW_DISAGREEMENT_UNRESOLVED`로 차단한다. 검수자를 2명으로 복제하거나 AI를 사람 검수자로 기록하지 않는다.

빈 검수 양식은 계획 JSON의 `review_record_example.record`에 있다. **실제 평가를 가장한 예제가 아니며 해시·권리·점수는 미입력**이다.
아래는 양식 일부를 읽는 방법이다. `null`을 실검수 후 1~5 정수와 `true/false`로 채운다.

```json
{
  "reviewer_id": "EXAMPLE_REVIEWER_A",
  "reviewer_type": "human",
  "scores": {
    "shape": null,
    "label_logo": null,
    "color_material": null,
    "reference_concept": null,
    "composition_copyspace": null
  },
  "fatal_flags": {
    "product_identity_changed": null,
    "critical_part_missing": null,
    "required_label_logo_changed": null,
    "unrequested_product_or_ad_text": null
  },
  "not_applicable": []
}
```

검수 기록에는 제품 ID·split·조건·원본/참고/결과 해시·결과 크기·요청 해시·설정 묶음 해시를 묶는다.
`rights_confirmed`는 그 사례에서 쓴 제품 사진과 참고 사진 모두에 대한 확인이다.
`beauty_ai.ad_evaluation`은 **명시한 사람 검수 기록의 산술과 필수 조건**만 검사한다. 이미지 내용을 읽거나 모델을 호출하지 않으며, 검수자의 신원·권리 증빙의 진위도 인증하지 않는다.
출력은 계속 `asset_approval=NOT_GRANTED`, `service_release_approval=NOT_GRANTED`다.

```sh
python -m beauty_ai.ad_evaluation outputs/reviews/one-case.json
```

파이썬에서는 `score_image_case(record)`, `evaluate_dataset(manifest, records)`로 단건과 평가셋을 계산한다.
정책 버전 v0.1의 비중·80점·보존 4점은 고정되어 있다. 바꾸면 새 버전으로 수정·검토하고 평가 주기를 분리한다.

## 5. FinOps 100점과 운영 중단선

**현재 7회 호출의 사용량 기반 추정치는 R&D 기록이다. 확정 청구액·팀 잔액·실제 성공 광고당 원가는 아직 확인되지 않았다.**

| 항목 | 내부 비중 | 임시 통과 기준 |
| --- | ---: | --- |
| 성공 광고당 총원가 | 30 | 사람이 인수한 최종 광고 1장당 **확정 가변비 ≤ $0.50** |
| 회피 가능한 낭비 | 20 | 확정 생산 비용 중 회피 가능한 실패·재시도 비용 **≤ 10%** |
| 팀 공유 예산 | 25 | 현재 2팀 키·잔액·공유 사용액 확인, **80% 경고 / 90% 신규 유료 호출 차단** 작동 검증, 인수 시 **소진율 90% 미만** |
| 청구 대조·원가 추적 | 25 | 정산 대상 영수증 **100% 대조**, 작업별 원가 추적, 전체 추정치와 실비의 오차 **≤ 20%** |

각 항목의 전체 조건을 충족하면 해당 배점, 확인된 실패면 0점이다. 미확인은 총점 `null`이다. 출시하려면 네 항목을 모두 통과해야 한다.
이진 배점은 임시 기준의 판정을 단순하게 만들기 위한 것이다. 수치가 근소하게 초과한 이유는 원자료와 함께 보고한다.

`$0.50`은 이미지 1회 가격이 아니다. 동일 회계 구간의 **LLM + 이미지 + 유료 렌더링/저장 + 귀속 가능한 가변 서빙 비용**을 생산 실패·재시도까지 포함해 합한 뒤, 인수된 최종 광고 수로 나눈다.
인수된 광고가 0장이면 분모가 없으므로 원가는 `null`이다. 제공받은 무료/선불 인프라와 배부 가정은 별도로 표시한다.
의도된 프리셋 비교·연구는 R&D로 구분한다. 생산 낭비에서 제외하더라도 팀 예산에서 사라지는 비용은 아니다.

회계 구간 ID를 고정한다. 전체 서비스 가변비와 **공유 OpenAI 키의 $30 예산**은 범위가 다르다.
`production_team_api_confirmed_usd`, `research_team_api_confirmed_usd`로 그 중 팀 OpenAI 비용을 분리한다.
팀 API 생산 비용은 전체 생산 비용을 넘을 수 없고, 두 팀 API 부분합은 확인된 누적 팀 사용액을 넘을 수 없다.
동일 시점의 누적 사용액과 남은 잔액이 $30으로 대조되어야 한다. 다른 팀원의 호출도 포함한 실제 공유 잔액이 필요하다.
잔액 조회 시각 `balance_checked_at`과 평가 기준 시각 `evaluation_as_of`를 시간대가 있는 ISO 8601 문자열로 기록한다.
평가 시점에서 잔액 조회가 **15분 이내**여야 한다. 시각이 없거나, 조회가 평가보다 미래이거나, 15분을 넘으면 `BLOCKED`다.
이 임시 유효기간은 기록된 평가 기준 시각에만 적용된다. 저장된 보고서를 나중의 호출 허가로 쓰지 말고, 실제 유료 호출 직전에는 공유 잔액과 진행 중 예약액을 다시 확인한다.

80%는 **$24 경고**, 90%는 **$27부터 신규 유료 호출 차단**이다. 현재 진행 중 호출의 최대 예약액까지 예산 통제에서 고려한다.
`evaluate_finops()`는 수치를 판정하는 오프라인 함수다. 실제 호출을 중단하는 런타임 장치의 작동은 별도 시험하고 `budget_controls_verified`로 기록한다.
기준 파일·평가 결과 자체가 유료 호출을 승인하거나 자동 실행하지 않는다.

청구 지연은 **24시간을 임시 대기 기준**으로 둔다. 그 이후 제공자 청구/사용 내역과 외부 요청 ID·작업 영수증을 대조한다.
대기 중 영수증은 숨기지 않고 `pending_within_billing_lag`로 남기며, 최종 인수는 대조가 끝날 때까지 차단한다.
청구가 집계되어 개별 호출 귀속을 확인할 수 없다면 정합성을 만들기 위해 임의 배분하지 말고 미확인으로 남긴다.
응답의 토큰 수와 단가를 곱한 값은 **추정치**다. 실제 청구로 취급하지 않는다.

추정 오차는 `abs(추정 생산비 - 확정 생산비) / 확정 생산비`다.
둘 다 **확정적으로 0**일 때만 오차 0, 실비가 0인데 추정치가 양수면 비율 미정으로 대조 조건 실패다.
미확인 실비를 0으로 넣어 통과시키지 않는다. 모든 비용은 음수·무한대·NaN을 허용하지 않는다.

## 6. 서비스 평가와 별도 필수 조건

정상 입력으로 최종 결과에 도달해야 하는 **20개 E2E 시나리오**를 먼저 고정한다.
그 중 **18개 이상(90%)**이 현재 revision의 사용자 검토를 거쳐 한글 4:5 광고·본문·태그 다운로드에 성공해야 한다.
예상된 잘못된 입력의 정상 거절은 별도 오류 처리 평가셋이며, 이 성공률 분모를 부풀리지 않는다.
실행하지 않은 사례와 결과 미확인은 성공으로 세거나 분모에서 빼지 않는다.

기계 처리 시간은 유효한 업로드 요청 접수부터 최종 다운로드 자산 준비까지이며, 큐·업로드/정규화·LLM·이미지·렌더링·저장·재시도를 포함한다.
기록된 사용자 검토 대기 구간만 제외한 합계를 사용한다. 사용자 대기를 포함한 실제 소요 시간도 따로 보고한다.
임시 기준은 **p95 ≤ 90초**다. 20개 종료 시간값을 정렬하여 19번째 값(nearest-rank)을 사용한다.
성공 사례만 고르지 않는다. 실패는 오류 종료까지 시간을 포함한다. 타임아웃·미완료·누락 시간은 별도 기록하고 지연 통과 판정을 차단한다.

처음 쓰는 **사용자 5명 중 4명 이상**이 진행자의 작업별 힌트나 대신 조작 없이 입력→검토→다운로드를 끝내야 한다.
제품 내 일반 도움말은 허용한다. 5명 모두의 결과, 도움, 소요 시간, 수정 횟수를 남긴다. 광고 매출·전환 개선을 입증한 것으로 해석하지 않는다.

서비스 내부 점수는 성공률·p95·초보 완주·텍스트/렌더러 담당 인수에 각각 25점이며, 네 조건 모두 필수다.
카피 품질·사실 및 효능/규정 표현은 김다혜 담당이 평가한다. 이미지 담당 점수로 이를 덮어쓰지 않는다.
`evaluate_service()`와 `evaluate_release()`는 이 증거를 모아 판정할 뿐 다른 담당자의 결과를 만들어내지 않는다.

## 7. 실행 순서와 마일스톤

1. **유료 호출 전:** 실제 팀 키·공유 잔액·LLM/이미지 예산 배분·호출별 상한·중단선을 확인한다. 빈 manifest와 검수 기록이 `BLOCKED`인지 먼저 확인한다.
2. **10/30 통합:** 실제품을 확보하고 개발 5개로 기준을 맞춘다. 입력·사용자 확인 revision·최종 한글 합성·다운로드·실패와 오래된 결과 차단을 공동 재현한다. 비용 영수증의 연결도 점검한다.
3. **11/6 디테일·고도화:** 설정을 고정한 홀드아웃 5개, 반복, 전체 시간·사용성·FinOps를 평가한다. 실패와 개선 전후를 남기고 각 담당이 인수한다.

날짜는 마일스톤이다. 준비가 끝나면 앞당겨 진행할 수 있다. 다만 호출 승인·예산·실제품 권리·홀드아웃 분리는 생략하지 않는다.
기본 이미지 20결과와 반복 추가분은 **계획 수량**이다. 반복은 기존 결과 3개를 재사용하면 추가 6회, 재사용할 수 없으면 추가 9회다. E2E 실행 비용은 별도다. 동일 실행이 양쪽 프로토콜을 충족할 때만 ID로 명시하여 재사용하고 비용을 이중 집계하지 않는다.
이 파일에는 계정 키·제품 원본·실제 검수자·실제 평가 결과가 없다.
