# 이미지 모델 담당 작업 체크리스트

## 1. 완성 단계부터 정의

**담당 팀원: pi · 담당 영역: 이미지 모델**

작성일: 2026-10-20 · 대상: 화장품 광고 생성 MVP · 관련 코드 브랜치: `plan/models`

pi는 모델 선정·누끼·배경 생성·제품 레이어 재합성·이미지 품질 평가를 맡고, 서버·자산·GPU 운영은 해당 담당과 연결한다. 텍스트 모델의 담당·산출물·일정은 2026-10-20 확인한 [김다혜의 텍스트 모델 체크리스트](https://app.notion.com/p/3ffb13f77dbd80e6a5eec41286b29aaa)를 비교 기준으로 삼는다. 제품 분석·카피·검수뿐 아니라 **영어 이미지 프롬프트 생성도 텍스트 담당의 계획에 포함**돼 있다. 기존 [llmTodo.md](llmTodo.md)는 pi 기준으로 작성한 로컬 참고 체크리스트이며, 새 팀원 문서의 담당·일정 합의를 대신하지 않는다.

이미지 계획 담당은 pi, 팀원 문서의 텍스트 담당은 김다혜로 구분한다. API·자산·렌더러의 실행/인수 담당과 파트 간 계약은 아래 확인 항목에서 합의한다.

| 단계 | 완성 상태 | 통과 조건 | 남겨야 할 증거 |
| --- | --- | --- | --- |
| 1. 계약·실행 조건 확정 | 무엇을 생성하고 어떤 모델·환경에서 실행할지 정해졌다 | 입력·출력 자산, 마스크 의미, 작업 해상도, 모델·파이프라인 버전, 품질·비용 기준을 합의했다 | 계약 예제, 파이프라인 설정, 평가셋과 수용 기준 |
| 2. 실제 이미지 생성 | 실제 모델·GPU로 이미지 처리 흐름이 동작한다 | 원본 입력 → 누끼 → 작업 캔버스 배치 → 배경 생성 → 승인 제품 재합성 → 결과 저장을 실행했다 | 입력·중간 레이어·최종 결과, seed·모델 버전·환경·실행 기록 |
| 3. 품질 검증 | 결과를 광고 편집에 쓸 수 있는지 평가했다 | 라벨·색·형태·경계·투명 용기·중복 제품·텍스트 여백을 고정 평가셋으로 검사하고 합의한 기준을 통과했다 | 사례별 품질 판정, 실패 이미지, 지연·VRAM·비용 측정 |
| 4. 팀 연동 완료 | API에서 안전하게 제출·조회하고 결과를 재사용할 수 있다 | 작업 중복 방지, 응답 유실, GPU 장애·재시작, 자산 권한, 최신 입력 확인, 렌더러 전달을 공동 검증했다 | 실제 서버 통합 결과, 복구 시나리오, 실행 명령, 인계 기록 |

**pi의 이미지 모델 담당 완료는 4단계까지 충족한 상태로 정의한다.** 이미지 한 장 생성 성공이나 HTTP 모의 테스트 통과만으로 완료 처리하지 않는다. GPU 인프라·API·DB·UI 담당의 구현이 필요한 항목은 공동 검증으로 마무리한다.

### 최종 완료 체크

- [ ] 필수 기능과 평가셋이 1~4단계의 합의한 기준을 통과했다.
- [ ] 모델·파이프라인·프리셋·템플릿·실행 환경과 결과 자산의 버전이 기록돼 있다.
- [ ] 필수 품질·장애 항목에 미해결 오류가 없고, 지원하지 않는 입력은 명확하게 반환한다.
- [ ] 팀원이 문서와 샘플 입력으로 실제 누끼·배경 생성·상태 조회를 재현했다.
- [ ] API·자산·렌더링 담당이 결과 연결을 확인했고, PM이 이미지 담당 범위 완료를 확인했다.

### 팀원 LLM 일정과 연결하는 방법

노션 원문의 계획은 **스키마 초안 10/23·확정 10/26, 제품 분석 10/27, 영어 이미지 프롬프트 10/28, 1차 규제 검수 10/29, FastAPI 연결 10/29–30**이다. Safe Zone·무드·카피 길이 합의는 11/02, LLM 검수·재작성 고도화는 11/02 주간, 최종 버전 고정·개발 마감은 11/10으로 적혀 있다. 아래 일정은 이를 반영한 **이미지 쪽 조정안**이며, 원문의 날짜를 바꾸거나 김다혜·서빙 담당이 이미 동의했다고 해석하지 않는다.

- 10/21은 이미지 측 계약 초안 작성, 10/23은 팀 초안과 예제 비교, 10/26은 교차 계약 v1 확정 목표로 구분한다. 10/23 첫 실제 이미지 생성은 고정 샘플 입력으로 진행해 LLM 기능 완성을 기다리지 않는다.
- 10/28에는 LLM 산출물 수신과 함수/adapter 수준 연결, 10/29–30에는 실제 API를 통한 공동 통합을 확인한다. 샘플 연결만 통과한 상태를 서비스 통합 완료로 표시하지 않는다.
- **합의 요청:** M1에 사용할 기본 고정 Safe Zone·무드 매핑·헤드/서브/CTA 길이 제한은 10/26까지 이미지·텍스트·렌더러 담당이 합의한다. 원문의 11/02 일정은 확장·디테일 개선으로 분리하는 제안이다. 이 조기 합의가 없으면 M1의 레이아웃/최종 출력 검증은 위험으로 남는다.
- M1은 사전·정규식 1차 검수의 범위와 승인 정책을 명시한다. LLM 검수·재작성까지 완료된 상태로 표시하지 않으며, 기존 검수 가드를 우회하거나 미완료를 `no_flags`로 바꾸지 않는다.
- **11/06은 이미지 담당 범위 완료**다. 함께 검증한 LLM·스키마·프롬프트 버전을 기록하고, 11/10까지 텍스트 쪽 변경이 발생하면 영향 범위 회귀를 다시 수행한다. 전체 서비스의 최종 버전 고정과 같은 의미로 사용하지 않는다.

이미지 일정은 **pi의 주 작업 계획**이며 김다혜의 LLM 작업 일정과 별도로 관리한다. 영어 프롬프트 생성기를 이미지 담당이 중복 구현하는 일정은 넣지 않는다. pi는 수신 프롬프트의 모델 적합성·토큰 처리·이미지 품질을 검증하고, API 담당은 검증된 프리셋·템플릿의 버전·좌표·해상도를 조립한다. API·영속 작업 저장·자산·렌더러는 10/21부터 병렬 준비하는 것을 제안하며, 각 담당의 실제 일정 합의는 위 항목에서 확인한다.

- [ ] 서버 기동, 모델 준비, 작업 제출·조회, 결과 열람, 재시작 복구 명령을 인계한다.

## 6. 유지해야 할 계약과 오류 의미

| 항목 | 현재 계약 | 구현·연동할 때 확인할 점 |
| --- | --- | --- |
| `AssetRef` | 자산 ID·SHA-256·크기·MIME | 실제 파일·권한과 일치하는지 서버에서 확인 |
| `CutoutRequest` | 원본 자산·파이프라인 ID/revision | 임의 모델 경로를 받지 않고 서버 프로필로 실행 |
| `CutoutResult` | 제품 RGBA·보호 마스크·수동 확인 여부·경고 | 사용자 확인 전 결과를 승인된 제품으로 간주하지 않음 |
| `BackgroundRequest` | 원본·승인 RGBA·보호 마스크·브리프·seed·프로필·선택적 ImagePrompt | 동일 작업 캔버스, 제품·텍스트 영역 검사. prompt가 있으면 내용·버전·revision을 hash에 포함; None은 기존 hash 유지 |
| `BackgroundResult` | 씬·제품 레이어·합성 preview·경고 | 현재 별도 품질 승인 필드는 없음. 승인 이력·차단은 서비스 계층 또는 합의한 스키마 확장으로 관리 |
| `ImageJob` | ID·입력 hash·상태·결과·오류 코드 | 성공만 결과를 공개, 실패·중단에는 오류 코드 필요 |
| `submit` | `PUT /internal/v1/jobs/{job_id}` | 접수 응답은 이미지 완성 증거가 아님. 서버가 durable idempotency를 구현해야 함 |
| `get` | `GET /internal/v1/jobs/{job_id}` | 응답 스키마와 작업 ID를 검사. 기대 요청을 받지 않으므로 입력 hash·작업 종류 대조는 별도 필요 |
| `wait` | 기대 요청을 받아 `get`을 반복 | 기대 입력 hash와 성공 결과 종류를 대조하며, 대기 종료와 작업 종료를 구분 |

- `IDEMPOTENCY_CONFLICT`: 같은 작업 ID가 다른 입력에 사용됐다.
- `SubmissionUncertain`: 접수 여부를 확정할 수 없다. 같은 ID의 상태를 확인한다.
- `JobStillPending`: 클라이언트의 대기 시간이 끝났다. 서버 작업은 계속 실행 중일 수 있다.
- `IMAGE_JOB_NOT_FOUND`: 조회 시 서버에서 작업을 찾지 못했다. 불명확한 제출과 연관된 경우 재제출 정책에 따라 조정한다.
- `IMAGE_PROTOCOL_ERROR`: ID·hash·타입·응답 구조 등 계약 불일치다. 정상 결과로 사용하지 않는다.

현재 프로토콜에 취소 API·진행률·업스케일 작업 종류는 없다. 필요하면 담당과 계약을 추가하고 구현·검증한다. 이미 제공되는 기능으로 설명하지 않는다.

## 8. 먼저 확정할 사항과 실행 순서

- [ ] 초기 제품 유형·광고 비율·출력 크기와 수동 확인 기준을 정한다.
- [ ] pi의 이미지 모델 범위와 백엔드·인프라·자산·렌더링 담당의 최종 분담을 확인한다.
- [ ] 실제 GPU 제공 환경·운영 담당·접근 방법·예산을 정한다.
- [ ] 누끼·배경 모델과 프로필 버전, 이미지 사용·모델 사용 조건을 확인한다.
- [ ] 품질·지연·VRAM·비용 목표와 평가 표본·판정자를 정한다.
- [ ] 작업 ledger·자산 저장·재시작 조정·렌더러 연결의 공동 담당자를 정한다.

모델 처리의 선행 순서: **자산·마스크 계약 확정 → 실제 GPU에서 누끼 → 작업 캔버스 승인 → 배경 생성·승인 제품 재합성 → 저장·편집·내보내기 연결 → 인계**.

서버·자산·렌더러는 10/21부터 병렬로 준비하고, 품질·성능 평가는 최초 실제 생성일부터 반복한다. 서버 중복 방지와 기본 장애 복구는 품질 개선이 모두 끝날 때까지 기다리지 않고 10/30 통합 전에 검증한다. 세부 기한은 2절의 일정표를 따른다.

체크박스는 실제 산출물과 검증 근거가 있는 경우에만 체크한다. 모델 후보 선정, 설치, 한 번의 생성 성공, 반복 품질 통과, 서버 연동 완료를 서로 다른 진행 상태로 기록한다.
