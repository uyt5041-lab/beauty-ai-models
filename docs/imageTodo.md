## 1. 완성 단계부터 정의

**담당 팀원: pi · 담당 영역: 외부 이미지 API 래퍼·이미지 품질·서비스 연결**

작성일: 2026-10-20 · SSOT 대조 갱신일: 2026-10-22 · 대상: 화장품 광고 생성 MVP · 팀 공유 계획: `plan/models` · 현재 구현: `feature/image-model`

pi는 외부 이미지 API의 기능 확인·요청/응답 변환·호출/결과 저장·제품 보존과 이미지 품질 평가를 맡는다. LLM 구현은 김다혜가 맡으며 pi는 산출물을 수신한다. OpenAI의 생성·편집·투명 배경 출력을 사용한다. 누끼도 생성형 API이며 제품 픽셀·라벨 보존을 보장하지 않는다. seed·제공자 job 조회·취소·3레이어 출력을 가정하지 않고 로컬 모델로 자동 대체하지 않는다. 서버·자산·렌더러 운영은 해당 담당과 연결한다. 텍스트 모델의 담당·산출물·일정은 2026-10-20 확인한 [김다혜의 텍스트 모델 체크리스트](https://app.notion.com/p/3ffb13f77dbd80e6a5eec41286b29aaa)를 비교 기준으로 삼는다. 제품 분석·카피·검수·한국어 이미지 프롬프트는 텍스트 담당이다. 영어 변환은 고도화 범위다. 기존 [llmTodo.md](llmTodo.md)는 pi 기준으로 작성한 로컬 참고 체크리스트이며, 새 팀원 문서의 담당·일정 합의를 대신하지 않는다.

이미지 계획 담당은 pi, 팀원 문서의 텍스트 담당은 김다혜로 구분한다. API·자산·렌더러의 실행/인수 담당과 파트 간 계약은 아래 확인 항목에서 합의한다.

**현재 완성 기준은 팀의 확정 SSOT다.** [SSOT 대조표](ssotAlignment.md)의 SSOT-01~12와 이 문서의 실행 항목을 함께 따른다. 기존 자산·작업 신뢰성·승인·revision/cache는 재사용 가능한 기반이며, 외부 요청 ID·과금·상태 조회와 연결하는 추가 계약이 필요하다. 내부 멱등성만으로 제공자의 중복 실행/과금 방지를 보장하지 않는다. 문서 대조는 새 기능 구현이나 팀 인수 완료를 뜻하지 않는다.

MVP의 최종 흐름은 **동일 제품 사진 2~5장·선택 참고 배경 0~5장·제품 정보 → 기획 AI 사전 조사 → 콘셉트/카피 1개 → 사용자 카피 검토 → 이미지 1개 → 사용자 이미지 검토 → 한글 카피 최종 합성 → 인스타그램 피드 4:5 광고 1개와 캡션·해시태그 확인/다운로드**다. 제품명·특징·광고 목적·기능성 여부를 받는다. 참고 배경은 색상뿐 아니라 배경 모습과 구도도 반영해야 한다.

제품 카테고리를 사전 선택하게 하거나 세부 품목을 미리 제외하지 않는다. 다양한 제품을 먼저 확보한 뒤 특성을 분류한다. 파일 손상·계약 위반의 오류와, 투명·반사·복잡한 구도 등의 **실제 품질 실패/수동 확인**을 구분한다. 경고가 있다고 품질 통과로 표시하거나 특정 품목의 일괄 제외로 바꾸지 않는다.

**중간 이미지와 최종 광고를 구분한다.** 이미지 모델은 광고 카피를 직접 그리지 않고 이미지 레이어와 문구 JSON을 렌더러에 전달한다. 사용자 이미지 검토 뒤 렌더러가 **한글 문구를 이미지 안에 합성하는 것이 MVP 필수**다. 중간 이미지의 무문구 원칙은 최종 결과에서도 문구를 빼라는 뜻이 아니다.

여러 후보 비교·부분 수정 UI·3:4 또는 다른 비율 선택·다른 플랫폼·병렬 생성은 후속 범위다. 이미 구현한 내부 revision/cache·늦은 결과 차단은 정확한 상태 연결을 위해 유지한다. 이 내부 기능의 존재를 부분 수정 UI 완성이나 MVP 다중 시안 제공으로 해석하지 않는다.


| 단계 | 완성 상태 | 통과 조건 | 남겨야 할 증거 |
| --- | --- | --- | --- |
| 1. 계약·실행 조건 확정 | SSOT 입력과 출력·단계별 검토를 계약으로 연결했다 | 동일 제품 2~5장, 참고 배경 0~5장, 제품 정보, 각 후보 1개, 최종 4:5·한글 합성·캡션/태그 및 운영 상한의 미합의 차이를 해결했다 | API-01~06·SSOT-01~12 인수 예제, 제공자 기능/캔버스 설정, 역할·평가 기준 |
| 2. 실제 이미지 생성 | 외부 API 래퍼가 SSOT 서비스 흐름 안에서 동작한다 | 검토된 카피·제품/참고 자산을 수신하고 제공자가 실제 지원하는 호출로 이미지1개를 생성·검증·저장했다. 제품 보존/합성 방식은 기능 확인 뒤 검증한다 | 실제 입력·결과·검토 상태, 제공자/모델·외부 요청 ID·지원하는 옵션·비용 상태 |
| 3. 품질 검증 | 다양한 실제 제품에서 광고 품질과 한계를 확인했다 | 형태·로고·라벨·색·경계·중복 제품·참고 구도·한글 여백을 평가하고, 사용자 이미지 검토와 합의 기준을 통과했다 | 권리 확보 평가셋, 사례별 판정·실패 기록, 지연·API 사용량/과금·재시도 비용 측정 |
| 4. 팀 연동 완료 | 검토된 광고 1개를 최종 합성·다운로드할 수 있다 | 기획→카피 검토→이미지 검토→한글 최종 합성→4:5 광고/캡션/태그 다운로드를 공동 검증했다. 내부 작업·권한·revision/cache·복구도 유지한다 | 전체 서비스 실행·최종 파일·검토 버전·복구 시나리오·팀 인계 기록 |

**pi의 이미지 모델 담당 완료는 4단계까지 충족한 상태로 정의한다.** 이미지 한 장 생성 성공이나 HTTP 모의 테스트 통과만으로 완료 처리하지 않는다. API·DB·UI·렌더러 담당의 구현이 필요한 항목은 공동 검증으로 마무리한다. GPU 인프라 구축은 현재 MVP 필수 범위가 아니다.

### 최종 완료 체크

- [ ] SSOT-01~12의 필수 기능과 평가셋이 위 1~4단계의 합의한 기준을 통과했다. 각 단계 후보는 1개이며 최종 광고는 4:5 한글 합성본이다.
- [ ] 제공자·모델 식별자·래퍼/요청 스키마·프리셋·템플릿·결과 자산 버전과 외부 요청 ID가 기록돼 있다. 제공자가 고정 버전이나 seed를 지원하지 않으면 미지원/재현 한계를 명시한다.
- [ ] 필수 품질·장애 항목에 미해결 오류가 없고, 파일/계약 오류와 품질 실패·수동 확인을 구분해 반환한다. 세부 품목을 사전에 제외하지 않는다.
- [ ] 팀원이 문서와 샘플 입력으로 실제 외부 API 호출·결과 저장·상태 조정을 재현했다. 누끼·마스크 등은 실제 지원·채택한 방식만 인수한다.
- [ ] API·자산·렌더링 담당이 결과 연결을 확인했고, PM이 이미지 담당 범위 완료를 확인했다.

현재 로컬 엔진은 실험/선택 경로로 보존하고, MVP에는 외부 API 래퍼와 SSOT 서비스 접점을 추가한다. 현재 제품 레이어의 사전 승인은 생성 후 **사용자 이미지 검토**를 대신하지 않는다. SDXL 고정 프로필은 각 축 512/768/1024와 B9의 정사각·512×768 실행을 검증했으며, 최종4:5를 검증한 것은 아니다.

근거: `beauty_ai/image_gateway.py`, `beauty_ai/image_integrity.py`, `beauty_ai/contracts.py`, `tests/test_wrappers.py`, `DESIGN.md`.

## 5. 단계별 구현 이력과 미완료 항목

이 절은 기존 기술 구현 근거를 보존한 목록이다. **2절의 날짜별 마일스톤 인수 체크와 별도**이며 구현된 순서만으로 일정 완료를 올리지 않는다. 실제 최신 구현은 feature/image-model 원본을 본다.

### SSOT 서비스 연결 실행 항목

아래 12개는 새로 대조한 **미완료 서비스 요구**다. 자세한 차이는 [SSOT 대조표](ssotAlignment.md)를 따른다. 기존 1-A~4-B는 재사용할 엔진과 검증의 하위 목록이며, 12개 항목을 문서에 적은 것만으로 구현·담당 수락·인수가 끝나지 않는다. API·UI·렌더러 담당의 실명과 수락은 SSOT-12에서 확인한다.

- [ ] **SSOT-01 · 동일 제품 2~5장 입력과 주제품 사진 전략.** 담당: API/자산/UI + pi, 제품 분석은 김다혜. 의존: product group·asset 목록·입력 확인 계약. 완료조건: 2~5장의 동일 제품 묶음·각도 정보를 받고 다른 제품 혼입/모호함을 확인 경로로 넘긴다. SSOT의 사진 검증 체크박스를 제공하되 품질 합격과 구분한다. 단일 주사진 선택 또는 여러 사진 활용 방식은 구현 전략으로 합의·검증하며 한 장만 받는 현재 엔진 호출을 전체 요구 충족으로 표시하지 않는다.
- [ ] **SSOT-02 · 입력 운영 상한과 사용자 안내.** 담당: API/인프라/UI + pi, 정책 수락은 PM. 의존: 원문 용량·해상도 제한 없음 요구와 현 decode/픽셀/메모리 가드 대조. 완료조건: 원본 보관·작업용 정규화·오류 안내·수용 가능한 운영 조건을 합의하고 경계값을 확인한다. 기존 보호 가드를 삭제하거나 실제 무한 자원을 보장한 것으로 처리하지 않는다. 입력 정보에도 SSOT상 별도 제한을 두지 않는 방향과 실제 검증 조건을 구분해 기록한다.

## 6. 유지해야 할 계약과 오류 의미

아래는 **현재 로컬/내부 계약**이다. 외부 API가 이 필드·마스크·seed·레이어·상태 조회를 모두 지원한다는 뜻이 아니다. 제공자별 입출력과 미지원 처리는 API-01~05에서 확정하며 기존 hash/snapshot 의미를 조용히 바꾸지 않는다.

| 항목 | 현재 계약 | 구현·연동할 때 확인할 점 |
| --- | --- | --- |
| `AssetRef` | 자산 ID·SHA-256·크기·MIME | 실제 파일·권한과 일치하는지 서버에서 확인 |
| `CutoutRequest` | 원본 자산·파이프라인 ID/revision | 임의 모델 경로를 받지 않고 서버 프로필로 실행 |
| `CutoutResult` | 제품 RGBA·보호 마스크·수동 확인 여부·경고 | 사용자 확인 전 결과를 승인된 제품으로 간주하지 않음 |
| `BackgroundRequest` | 원본·승인 RGBA·보호 마스크·브리프·seed·프로필·선택적 ImagePrompt | 동일 작업 캔버스, 제품·텍스트 영역 검사. prompt가 있으면 내용·버전·revision을 hash에 포함; None은 기존 hash 유지 |
| `BackgroundResult` | 씬·제품 레이어·합성 preview·경고 | 현재 별도 품질 승인 필드는 없음. 승인 이력·차단은 서비스 계층 또는 합의한 스키마 확장으로 관리 |
| `ImageJob` | ID·입력 hash·상태·결과·오류 코드 | 성공만 결과를 공개, 실패·중단에는 오류 코드 필요 |
| `submit` | `PUT /internal/v1/jobs/{job_id}` | 접수 응답은 이미지 완성 증거가 아님. 서버가 durable idempotency를 구현해야 함 |
| `get` | `GET /internal/v1/jobs/{job_id}` | 응답 스키마와 작업 ID를 검사. 기대 요청을 받지 않으므로 입력 hash·작업 종류 대조는 별도 필요 |
| `wait` | 기대 요청을 받아 `get`을 반복 | 기대 입력 hash와 성공 결과 종류를 대조하며, 대기 종료와 작업 종료를 구분 |
| `submit_and_wait` | 하나의 deadline·PUT 1회·동일 ID GET | 404만으로 미접수/재제출 판정하지 않음. 유효 job 미관찰은 SubmissionUncertain, 관찰 후 미완료는 JobStillPending |

- `IDEMPOTENCY_CONFLICT`: 같은 작업 ID가 다른 입력에 사용됐다.
- `SubmissionUncertain`: 접수 여부를 확정할 수 없다. 같은 ID의 상태를 확인한다.
- `JobStillPending`: 클라이언트의 대기 시간이 끝났다. 서버 작업은 계속 실행 중일 수 있다.
- `IMAGE_JOB_NOT_FOUND`: 조회 시 서버에서 작업을 찾지 못했다. 불명확한 제출과 연관된 경우 `submit_and_wait`는 같은 ID로 제한 시간 안에서 재조회한다. 자동 PUT 재전송·새 ID 발급은 하지 않는다.
- `IMAGE_PROTOCOL_ERROR`: ID·hash·타입·응답 구조 등 계약 불일치다. 정상 결과로 사용하지 않는다.

현재 프로토콜에 취소 API·진행률·업스케일 작업 종류는 없다. 필요하면 담당과 계약을 추가하고 구현·검증한다. 이미 제공되는 기능으로 설명하지 않는다.

### 8.2 기존 실행 순서

현재 실행 순서는 **API-01 제공자 기능 확정 → API-02~05 래퍼·인증/예산·외부 제출 조정·결과 저장 → API-06 실호출/품질 인수**다. SSOT-01~12의 입력·검토·최종 출력 요구를 병행 연결한다. 기존 내부 기반은 재사용하고 로컬 GPU 엔진 개선은 필수 순서에 넣지 않는다.

- [ ] 사전 품목 제외 없이 실제 제품 평가 분류·수동 확인 기준과 최종4:5 출력 크기를 정한다.
- [ ] pi의 이미지 모델 범위와 백엔드·인프라·자산·렌더링 담당의 최종 분담을 확인한다.
- [ ] **자체호스팅 재선택 시에만:** 실제 GPU 제공 환경·운영 담당·접근 방법·예산을 정한다.
- [ ] 선정한 OpenAI의 실제 계정 모델 권한·사용/보관 조건·잔액을 확인하고, 호출을 허용받은 뒤 누끼와 생성 품질을 평가한다. 제공자 선정과 오프라인 구현은 완료했다.
- [ ] 품질·지연·API 사용량/비용 목표와 평가 표본·판정자를 정한다. VRAM은 자체호스팅 재선택 때만 적용한다.
- [ ] 작업 ledger·자산 저장·재시작 조정·렌더러 연결의 공동 담당자를 정한다.

서비스의 선행 순서: **동일 제품/참고 배경·제품 정보 입력 → 기획 조사 → 카피1개 생성·사용자 검토 → 외부 API·확정한 제품 보존/합성 방식으로 이미지1개 생성 → 사용자 이미지 검토 → 한글 최종 합성 →4:5 광고·캡션/태그 확인/다운로드 → 인계**. 제품 레이어 승인과 최종 이미지 검토는 서로 다른 상태다.

서버·자산·렌더러는 10/21부터 병렬로 준비하고, 품질·성능 평가는 최초 실제 생성일부터 반복한다. 서버 중복 방지와 기본 장애 복구는 품질 개선이 모두 끝날 때까지 기다리지 않고 10/30 통합 전에 검증한다. 세부 기한은 2절의 일정표를 따른다.

체크박스는 실제 산출물과 검증 근거가 있는 경우에만 체크한다. 모델 후보 선정, 설치, 한 번의 생성 성공, 반복 품질 통과, 서버 연동 완료를 서로 다른 진행 상태로 기록한다.

- [ ] **배치 3 / 원형 보존:** 전체 비율·각도·뚜껑/본체 폭·색·재질을 원본과 비교한다. 외부 API 누끼를 사진 해시로 캐시하고 원본 고정 합성 방식을 검증한다.

- [ ] **배치 4 / 이미지 연출 실험:** 카피를 재작성하지 않고 색·톤, 형태 관계, 서체, 콘셉트, 소품을 비교한다. 봄빛은 봄의 계절 단서와 빛을 함께 평가한다. 실험 결과를 바로 팀 필수 계약으로 만들지 않는다.
